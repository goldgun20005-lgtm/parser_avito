# ARCHITECTURE_AUDIT — Аудит архитектуры

> Статус: **Подтверждено кодом**. Для каждого модуля: назначение, вход/выход, зависимости,
> точки отказа, расширяемость, необходимость доработки под серверный сценарий.

## Общая оценка

Архитектура для скрипта **выше среднего**: с версии 3.2.0 проведён рефакторинг, выделены
абстракции `Notifier`, `ResultStorage`, `CookiesProvider`, `Proxy` с фабриками. Это даёт
хорошую расширяемость для уведомлений/экспорта/cookies/прокси **без правки ядра**.

Слабые места: бизнес-логика и оркестрация (бесконечный цикл) смешаны в `parser_cls.py`;
хранилище «просмотренных» (SQLite) намеренно не абстрагировано и завязано на singleton с
фиксированным именем файла; нет слоя конфигурации через ENV; нет тестов; порядок
«уведомить → сохранить» создаёт риск потери данных и дублей.

## Модули

### `parser_cls.py` — ядро + оркестратор
- **Назначение:** класс `AvitoParse` (вся бизнес-логика парсинга) + `__main__` (бесконечный цикл).
- **Вход:** `AvitoConfig`, опционально `stop_event` (для GUI).
- **Выход:** побочные эффекты — уведомления, запись в SQLite, Excel, логи.
- **Зависимости:** все фабрики, `HttpClient`, `AdsFilter`, `SQLiteDBHandler`, модели.
- **Точки отказа:** `find_json_on_page` (изменение разметки Avito → пустой JSON → нет объявлений);
  `ItemsResponse(**catalog)` (изменение структуры → `ValidationError`, см. #306/#307);
  порядок notify→save (потеря данных/дубли #300); `self.stop_event = True` (строка 197) —
  затирает Event булевым значением (баг, безвреден в CLI, сомнителен в GUI).
- **Расширяемость:** средняя — оркестрация (цикл, расписание) зашита в `__main__`.
- **Доработка под сервер:** вынести цикл/расписание из ядра; поменять порядок save→notify;
  добавить graceful shutdown по SIGTERM.

### `AvitoParser.py` — GUI (Flet)
- **Назначение:** desktop-интерфейс: редактирование конфига, тест TG/VK, логин в аккаунт, запуск парсера в потоке.
- **Вход/выход:** читает/пишет `config.toml`; запускает `AvitoParse.parse()` в `threading.Thread`.
- **Зависимости:** `flet`, `parser_cls`, фабрики уведомлений, `prompt_user_login` (Playwright).
- **Точки отказа:** требует GUI-среду; `telegram_log_test` собирает `tg_chat_id` через `.split()` (по пробелам, не по строкам) — мелкая несогласованность с `save_config` (там `.splitlines()`).
- **Расширяемость:** низкая (монолитный `main()` ~720 строк).
- **Доработка под сервер:** **не нужен на сервере** — сервер использует `parser_cls.py`.

### `config.toml` + `load_config.py` + `dto.py`
- **Назначение:** конфигурация. `tomllib` читает, `tomli_w` пишет; `AvitoConfig` (dataclass) — типизация.
- **Точки отказа:** нет валидации значений (напр. отрицательные паузы, кривые URL); секреты в открытом TOML;
  `AvitoConfig` — dataclass без валидации (в отличие от моделей на Pydantic).
- **Доработка под сервер:** поддержка ENV/`.env` для секретов; валидация; `config.example.toml`.

### `models.py` — Pydantic-модели
- **Назначение:** строгая типизация ответа Avito (`Item`, `ItemsResponse`, `PriceDetailed`, …).
- **Точки отказа:** **главный источник хрупкости** — поля Avito меняются, и `ItemsResponse(**catalog)`
  падает с `ValidationError` (issues #305/#306/#307). Многие поля уже сделаны `Optional`, но не все.
- **Расширяемость:** добавление полей тривиально.
- **Доработка:** сделать модель максимально терпимой (`model_config = ConfigDict(extra="ignore")`,
  больше `Optional`/значений по умолчанию), либо парсить «лениво».

### `db_service.py` — SQLite (память просмотренных)
- **Назначение:** singleton `SQLiteDBHandler`, таблица `viewed(id INTEGER, price INTEGER)`; проверка/запись.
- **Вход:** `Item` (id, priceDetailed.value). **Выход:** bool «видели/нет».
- **Точки отказа:**
  - таблица **без PRIMARY KEY/UNIQUE** → `INSERT OR REPLACE` работает как обычный `INSERT` →
    дубли строк, неограниченный рост БД;
  - фиксированное имя `database.db` в CWD (singleton) → нельзя несколько независимых наборов в одном процессе;
  - конкурентная запись несколькими процессами/контейнерами → `database is locked` (нет WAL).
- **Расширяемость:** **намеренно не абстрагировано** (см. `docs/DOCS.md` п.6).
- **Доработка под сервер:** добавить `PRIMARY KEY(id, price)`/`UNIQUE`, индексы, WAL, очистку старых записей;
  при мульти-пользователе — вынести в PostgreSQL.

### `parser/http/client.py` — HTTP-клиент (`curl_cffi`)
- **Назначение:** запросы с имитацией браузера, ретраи, реакция на блокировки.
- **Вход:** метод/URL/params + провайдеры cookies и proxy. **Выход:** `Response` или `RuntimeError`.
- **Точки отказа:** на каждый запрос создаётся новая сессия (нет keep-alive); счётчик блокировок
  `_block_attempts` общий на инстанс; при исчерпании ретраев — `RuntimeError` (ловится только в `fetch_data`,
  но **не** в `fetch_api_data` → исключение всплывёт в `parse`, поймается верхним `try` цикла `__main__`).
- **Расширяемость:** хорошая (инкапсулировано).
- **Доработка:** экспоненциальный backoff + jitter, единая обработка ошибок API-страниц, метрики 403/429.

### `parser/cookies/` — провайдеры cookies
- **`base.CookiesProvider`** — абстракция (`get`, `update`, `handle_block`).
- **`own_cookies.OwnCookiesProvider`** — свои cookies из `storage/own_cookies.json`, атомарное сохранение,
  `atexit`-сохранение. `handle_block` = просто пауза.
- **`external_api.ExternalApiCookiesProvider`** — интеграция с **spfa.ru**: покупка cookies, разблокировка,
  история кодов, cooldown покупки 10 мин.
- **`factory.build_cookies_provider`** — выбор по `use_bypass_api` / `use_own_cookies`.
- **Точки отказа:** жёсткая зависимость от внешнего сервиса spfa.ru (платный, сторонний); `OwnCookiesProvider.get`
  кидает исключение, если cookies нет.
- **Расширяемость:** высокая (новый провайдер = новый класс + строка в фабрике).

### `parser/proxies/` — прокси
- **`NoProxy` / `ServerProxy` / `MobileProxy`** + `proxy_factory.build_proxy`.
- **Назначение:** статический/мобильный прокси, смена IP по ссылке (`handle_block`).
- **Точки отказа:** `MobileProxy.handle_block` ждёт `new_ip` в JSON; формат прокси строго `user:pass@host:port`
  (проверка в GUI `check_string`).
- **Расширяемость:** высокая. Нет пула/ротации нескольких прокси (только один).

### `parser/export/` — экспорт результатов
- **`base.ResultStorage`** (абстракция) → **`ExcelStorage`** (openpyxl, потокобезопасно через `Lock`,
  защита от формул `excel_safe`) → **`CompositeResultStorage`**, **`NullResultStorage`** → `factory`.
- **Точки отказа:** Excel целиком загружается в память (`load_workbook`) при каждом сохранении —
  на больших файлах деградация; нет CSV/JSON/БД-экспорта (только XLSX).
- **Расширяемость:** **отличная** — добавить CSV/JSON/Postgres = новый класс `ResultStorage` + фабрика.

### `filters/ads_filter.py` — фильтрация
- **Назначение:** конвейер фильтров (`apply`): просмотренные → цена → стоп-слова → ключевые → гео → продавец → возраст → резерв → продвижение.
- **Точки отказа:** `_filter_by_recent_time` делит `ad.sortTimeStamp/1000` без проверки на None
  (если поле None и `max_age>0` → `TypeError`); `_filter_by_address` обращается к `ad.geo` как к dict
  через `getattr(...).get(...)`, хотя `geo` — Pydantic-модель `Geo` (риск, что фильтр всегда отсекает/пропускает).
- **Расширяемость:** хорошая (добавить метод-фильтр в список).

### `integrations/notifications/` — уведомления
- **`base.Notifier`** (абстракция + `notify_many` + `format`), **`telegram.py`**, **`vk.py`**,
  **`composite.py`**, **`transport.send_with_retries`**, **`utils`** (MarkdownV2-экранирование).
- **Точки отказа:** Telegram-токен в URL запроса; `notify_many` шлёт по одному (медленно при больших пачках);
  ошибки уведомления глушатся в `CompositeNotifier` (лог + продолжаем) — уведомления могут «молча» не дойти.
- **Расширяемость:** **отличная** (см. ответы ниже).

### `utils/`
- `build_api_params` / `normalize_parametr` — формирование query для API-пагинации (хрупко к изменениям Avito).
- `parse_phone` — **отключён** в коде.
- `prompt_user_login` — Playwright-логин (headed-браузер) → `storage/own_cookies.json`. **Не работает в headless-Docker.**

### `hide_private_data.py`
- Маскирование секретов в логах (regex). Покрывает прокси, tg_token, tg_chat_id, proxy_change_url, password/token/api_key/secret.
- **Замечание:** маскирование применяется только в `log_config` (стартовый лог). Прочие места логирования не проходят через маску.

## Ответы на ключевые архитектурные вопросы

| Вопрос | Ответ |
|---|---|
| Где основная бизнес-логика? | `parser_cls.py` (`AvitoParse`), фильтры в `filters/`, модели в `models.py`. |
| Связан ли парсер с GUI? | **Нет жёсткой связи.** GUI импортирует `AvitoParse`, но `parser_cls.py` запускается полностью независимо. |
| CLI независим от GUI? | **Да.** `python parser_cls.py` не требует Flet-окна (хотя `flet` есть в зависимостях). |
| Как устроены уведомления? | Абстракция `Notifier` + фабрика по конфигу + `CompositeNotifier` рассылает во все каналы. |
| Как добавить новый тип уведомлений? | Новый класс `XNotifier(Notifier)` с методом `notify(ad, message)` + строка в `factory.py` (+ GUI при PR). Ядро не трогаем. |
| Как добавить новый способ сохранения? | Новый класс `XStorage(ResultStorage)` с `save(ads)` + фабрика `export/factory.py`. |
| Можно добавить PostgreSQL? | **Да** — как `ResultStorage` (для результатов) и/или заменив `SQLiteDBHandler` (для «просмотренных»). Второе потребует абстрагирования хранилища просмотренных (сейчас его нет). |
| Telegram-бот с кнопками? | **Да, но это новый компонент.** Текущий `TelegramNotifier` шлёт через REST без inline-кнопок и без приёма апдейтов. Нужен отдельный бот (aiogram/python-telegram-bot) — см. `IMPROVEMENT_ROADMAP.md` P3. |
| Webhook? | **Да** — тривиально как новый `Notifier` (POST в URL). |
| n8n? | **Да** — через Webhook-нотификатор → n8n webhook node. |
| REST API? | **Не из коробки.** Требует отдельного слоя (FastAPI) поверх ядра. См. вариант 3 в `DEPLOYMENT_OPTIONS.md`. |
| Очередь обработки? | **Нет.** Сейчас последовательный цикл. Очередь (Redis/Celery) — это P2/P3 переработка. |
| Несколько пользователей? | **Нет.** Один глобальный `config.toml`, один `database.db`. Мультиарендность не поддержана. |
| Несколько независимых наборов ссылок? | Частично: все URL в одном списке `config.urls`, но дедуп/Excel общие. Раздельные наборы с раздельными настройками — нет. |
| Несколько экземпляров одновременно? | Технически можно (разные каталоги/конфиги), но они **не должны делить один `database.db`**. |
| Безопасно ли нескольким инстансам делить одну SQLite? | **Нет.** Нет WAL, нет уникального ключа, риск `database is locked` и гонок. Для конкуренции — PostgreSQL. |
