## P0 / критичные для круглосуточной эксплуатации

### #300 — Объявления помечаются просмотренными ДО записи в файл (потеря данных)
- **Дата:** 2026-05-13. **Статус upstream: ОТКРЫТ. В нашем форке: ✅ ИСПРАВЛЕНО** (коммит на ветке
  `claude/gracious-gauss-rnq17p`). Порядок изменён на **save → notify → mark_viewed**, сохранение
  результата перенесено на каждую страницу (а не в конец ссылки). Гарантия at-least-once:
  при сбое возможен дубль, но не потеря. Проверено кодом + статической проверкой порядка.
- **Где:** `parser_cls.py` — `notify_many` (стр. 172) и `__save_viewed` (стр. 181) выполняются
  **до** `result_storage.save(ads_in_link)` (стр. 189, в конце обработки ссылки).
- **Суть:** если процесс упадёт/перезапустится между `__save_viewed` и `save` → объявление уже
  в `viewed`, но не в Excel. На следующем проходе фильтр «просмотренные» его отсечёт → **потеря результата**.
- **Связано:** #298 (closed) «Ничего не сохраняется в Excel при 10/100 страниц».
- **Критичность для вас:** высокая, если Excel/файл — важный канал. Для «только TG-уведомлений» — меньше.
- **Исправление:** менять порядок (save → notify → mark_viewed) и/или атомарно. См. `IMPROVEMENT_ROADMAP.md` P0.

### Дубликаты уведомлений при сбое
- **Статус: ✅ СНИЖЕНО** в форке. После fix #300 порядок save→notify→mark означает at-least-once:
  дубль возможен только при сбое между notify и mark (редко) и предпочтительнее пропуска уведомления
  для мониторинга. Рекомендуется доп. dedup в n8n как страховка.

### #307 / #306 — Pydantic «Field required [type=missing]» (свежие, 2026-06-29)
- **Статус upstream: ОТКРЫТЫ. В форке: ✅ СМЯГЧЕНО.**
- **Было:** `ItemsResponse(**catalog)` падал целиком на одном «битом» объявлении → вся страница терялась.
- **Сделано:** `_parse_items_tolerant()` парсит объявления по одному, пропуская некорректные;
  `Item.model_config = extra="ignore"` (неизвестные поля Avito игнорируются). Теперь одно битое
  объявление не роняет страницу. Проверено тестом (T9: 1 битый из 3 пропущен, 2 валидных сохранены).
- **Остаточный риск:** если Avito изменит **обязательное** поле во ВСЕХ объявлениях — они все будут
  пропущены (0 результатов + WARNING в логах), но без краша. Полное лечение — ослабить обязательность
  полей `PriceDetailed`/`Category`/… (P1.5 продолжение). **Требует боевой проверки на сервере.**

### Рост `database.db` без ограничений
- **Статус: ✅ ИСПРАВЛЕНО** в форке. Добавлен `PRIMARY KEY (id, price)`, `INSERT OR IGNORE`,
  режим WAL и **авто-миграция** старых БД (дедуп существующих строк при старте). Проверено тестом
  (старая БД 4 строки → 2 после миграции). Авто-очистка старых записей по времени — отдельная задача (P2).

### Повреждение SQLite / перезапуск контейнера
- **Статус: Подтверждено кодом + конфигурацией.**
- **Суть:** нет WAL; при `docker-compose.yml` БД монтируется bind-mount с `create_host_path: false`
  (файл `database.db` должен существовать заранее, иначе сбой). При жёстком kill во время записи —
  риск повреждения. Дедуп работает по `(id, price)` — при потере БД пойдут повторные уведомления.

## Что особенно проверить (по запросу аудита)

| Вопрос | Ответ по коду |
|---|---|
| Сначала сохраняются данные или помечаются просмотренными? | **Сначала уведомление, затем mark_viewed, и только в конце ссылки — запись в Excel.** Это и есть корень #300. |
| Возможна ли потеря результатов при исключении? | **Да** (между mark_viewed и save Excel). |
| Возможны ли дубликаты уведомлений? | **Да** (сбой между notify и mark_viewed). |
| Что при повреждении SQLite? | Потеря памяти «просмотренных» → массовые повторные уведомления; при ошибке записи — лог, проход продолжается. |
| Что при перезапуске контейнера? | Данные сохраняются, если `database.db`/`result`/`storage` на volume. Иначе — теряются (см. `DOCKER_AUDIT.md`). |
