# MONITORING — Мониторинг и алертинг

> Статус: технический раздел готов; выбор стека (простой/расширенный) — по масштабу.

## Что отслеживать (минимум)

| Метрика | Источник | Как получить |
|---|---|---|
| Контейнер запущен | Docker | `docker ps` / healthcheck |
| Процесс парсера жив | процесс | PID / heartbeat-файл (доработка P0.4) |
| Время последнего успешного цикла | лог | строка статистики в `logs/app.log` |
| Кол-во хороших/плохих запросов | лог | `good_request_count` / `bad_request_count` (логируются в конце прохода) |
| Число 403 / 429 / таймаутов | лог | warning-строки `Запрос заблокирован (…)` / `Request error` |
| Telegram/VK ошибки | лог | `[notify retry] …`, `VK API error …` |
| Размер `database.db` | ФС | `du -h database.db` |
| Размер логов | ФС | `du -sh logs/` |
| Свободное место на диске | ОС | `df -h` |
| CPU / RAM контейнера | Docker | `docker stats` |
| Число рестартов контейнера | Docker | `docker inspect -f '{{.RestartCount}}' avito` |

> ⚠️ Сейчас в коде **нет heartbeat и нет healthcheck** (P0.4). Пока они не добавлены, основной
> сигнал «жив/работает» — свежесть записей в `logs/app.log` и `RestartCount`.

## Вариант 1 — простой (рекомендуется для личного/надёжного использования)
- **Docker logs + ротация** (`logging.max-size/max-file` в compose).
- **Cron-скрипт** проверяет:
  - что контейнер `running`;
  - что `logs/app.log` обновлялся за последние N минут (иначе — парсер «встал»);
  - свободное место и размер БД.
  При проблеме — отправляет **Telegram-alert** (отдельный бот/чат для алертов).
- **Uptime Kuma** (или аналог) — отдельный лёгкий контейнер для дашборда/пингов.

Пример cron-проверки «парсер не встал»:
```bash
#!/usr/bin/env bash
LOG=/opt/parser_avito/logs/app.log
# если лог не менялся 15 минут — алерт
if [ -z "$(find "$LOG" -mmin -15)" ]; then
  curl -s "https://api.telegram.org/bot$ALERT_TOKEN/sendMessage" \
       -d chat_id="$ALERT_CHAT" -d text="⚠️ Avito parser: нет активности в логах >15 мин"
fi
```

Healthcheck (после внедрения heartbeat-файла, кандидат для compose):
```yaml
healthcheck:
  test: ["CMD-SHELL", "test $(find /app/logs/app.log -mmin -15 | wc -l) -gt 0"]
  interval: 60s
  timeout: 10s
  retries: 3
  start_period: 60s
```
> Это «прокси-healthcheck» по свежести логов. Точный healthcheck появится после P0.4 (heartbeat последнего успешного цикла).

## Вариант 2 — расширенный (для сервиса/нескольких воркеров)
- **Prometheus** — метрики (через экспортер; парсеру нужен `/metrics` endpoint — доработка).
- **Grafana** — дашборды (запросы, 403/429, найдено/уведомлено, CPU/RAM).
- **Loki + Promtail** — централизованные логи.
- **Alertmanager** — алерты (рост ошибок, простой, заполнение диска).
- Структурированные логи (loguru → JSON) для разбора в Loki.

## Алерты, которые стоит настроить
- Парсер не делал успешных запросов > N минут.
- Доля 403/429 за окно > X% (вероятная блокировка/исчерпание прокси).
- Баланс spfa.ru/прокси заканчивается (по логам ошибок 403 от сервиса).
- Контейнер перезапускался > N раз за час.
- Свободное место на диске < Y ГБ; `database.db`/логи растут аномально.
- Telegram/VK ошибки отправки.

## Минимально для старта
Простой вариант (Docker logs + cron + Telegram-alert + Uptime Kuma) закрывает 90% потребностей
одиночного развёртывания. Расширенный стек — только при переходе к сервису.
